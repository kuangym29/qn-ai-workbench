# QN AI 内容工作台 V2 架构设计基线

日期：2026-10-12  
状态：方案 A 已确认，历史业务数据允许清空，进入实施计划前正式设计基线  
仓库：`kuangym29/qn-ai-workbench`

---

## 1. 项目目标

QN AI 内容工作台 V2 继续定位为**轻量内容生产控制台**，不是复杂项目管理系统，也不是 AI 模型运行平台。

AI / ChatGPT Work / 其他创作工具负责内容生产与执行；工作台负责：

- 灵感、选题、正式内容的来源关系；
- 不同渠道 / 内容形式的生产分支；
- 正式内容与版本；
- 图片 / 视频批次生产；
- 审核、返修、发布状态；
- 人物 / 场景等长期复用资产的存在性与关联；
- AI 任务快照、版本历史与追溯；
- 一两人团队日常使用所需的“进行中 / 待我审核”视图。

核心原则：

> **后台可以严谨，前台必须轻量；能由系统或 AI 自动完成的，不要求用户重复填写。**

---

## 2. 已确认的产品主链

V2 主链固定为：

```text
灵感
↓
选题池
↓
开始创作
↓
选择渠道 / 内容形式
↓
一个正式 Content Item
↓
各渠道 / 内容形式分别制作
↓
审核
↓
发布
↓
归档
```

规则：

- 灵感池极轻量；
- 选题池只保留“待选 / 暂存”，备用采用星标，不单独做状态；
- 点击“开始创作”时选择渠道 / 内容形式；
- 后续允许追加渠道 / 内容形式；
- 一个选题进入正式生产后只建立一个 Content Item；
- 不因公众号、视频号、小红书分别复制多个 Content Item。

---

## 3. 方案 A：保留 V1 有价值底座，V2 重做业务层

正式采用方案 A。

### 3.1 保留的 V1 能力

继续复用：

- Laravel / Vue / Inertia / TypeScript / MySQL 技术栈；
- Auth / 登录；
- Project 最高隔离边界；
- ContentColumn；
- Topic 的基础概念；
- ContentItem；
- ContentPage 稳定页面身份思想；
- ContentCopyRevision / ContentPageVersion 的不可变版本思想；
- SourceReference；
- Duplicate Review / 查重能力；
- File / Asset / AssetVersion 的 append-only 版本思想；
- MySQL 8.4、Feature、Integration、Concurrency 测试经验与可复用测试设施。

### 3.2 不做历史数据兼容

用户已确认：**V1 历史业务数据可以直接清空。**

因此 V2 不需要：

- 旧数据 backfill；
- V1 / V2 双轨长期兼容；
- 为旧 ProductionTask / ChannelTask 保留前台兼容入口；
- 为旧 Asset 关系保留桥接表；
- 为旧状态机保留兼容判断。

开发与上线切换时允许使用 fresh database / schema reset 方式建立 V2 基线。

Git 历史仍然保留，因此旧实现需要追溯时可从版本库查看，不需要把废弃代码长期留在运行时代码中。

### 3.3 冗余代码清理原则

正式约束：**V2 替代后，删除不再使用的 V1 业务代码。**

删除范围包括但不限于：

- 旧 Production Workspace；
- 仅服务旧 ProductionTask / ChannelTask 状态机的前后端逻辑；
- 旧渠道硬编码；
- 已被新模型替代的 API client / controller / resource / request；
- 已被新测试覆盖的旧业务测试；
- 已失效的旧业务文档和 mock 数据；
- 没有调用方的旧组件、枚举和辅助函数。

但不做无关重构。删除前必须满足：

1. V2 等价能力已经实现；
2. 当前代码无调用；
3. 测试已覆盖新路径；
4. fresh install 可正常建立数据库并通过验收。

## 4. V2 核心业务对象

> 以下为后台架构概念，默认不直接以技术名暴露给日常用户。

### 4.1 Inspiration（灵感）

用途：记录最轻量的内容起点。

前台主要内容：

- 一句话灵感；
- 可选补充备注；
- 可选标签 / AI 建议；
- 创建时间系统自动记录。

灵感本身不需要复杂状态。

灵感可产生一个或多个 Topic，来源关系长期保留。

### 4.2 Topic（选题）

复用现有 Topic 概念，但前台简化为“选题池”。

正式状态：

- 待选；
- 暂存。

另有：

- `备用` 星标；
- 是否已经生成 Content Item，由关联关系自动判断，不要求用户维护“创作中”等状态。

### 4.3 ContentItem（内容母体）

Content Item 是同一主题的唯一正式内容母体。

前台只维护：

- 内容名称；
- 核心表达；
- 整篇故事线。

系统关联 / 自动显示：

- Project；
- 栏目；
- 来源灵感；
- 来源选题；
- 创建时间；
- 正式版本；
- 已选择渠道 / 内容形式；
- 页面数量；
- 生产与审核状态。

### 4.4 ContentBranch（渠道内容分支）

新增“渠道 + 内容形式”层，用于表达同一个 Content Item 在不同渠道、不同内容形式下的生产分支。

示例：

```text
Content Item
├ 微信公众号 · 图片文章（小绿书）
├ 微信公众号 · 图文文章
└ 微信视频号 · 视频
```

首批：

- `wechat_official + image_post`
- `wechat_official + article`
- `wechat_channels + video`
- `xiaohongshu` 作为预留渠道，具体内容形式后续启用。

同一渠道允许多个不同内容形式。

前台不显示 ContentBranch 技术名，只显示用户可理解的渠道 / 内容形式。

## 5. 渠道与内容形式

### 5.1 微信公众号

首批正式支持：

1. 图片文章（小绿书）
2. 图文文章

允许同时选择。

### 5.2 微信视频号

首批内容形式：视频。

### 5.3 小红书

先保留渠道能力，不提前增加复杂内容模型。

### 5.4 选择时机

点击“开始创作”时选择渠道 / 内容形式。

后续允许新增渠道 / 内容形式。

停止某个分支时保留该分支已有历史版本，不要求用户手工同步其他分支状态。

---

## 6. 公众号图片文章（小绿书）

### 6.1 页面类型

继续使用稳定页面身份。

页面类型：

- 封面；
- 正文；
- 专属收尾；
- 固定封底。

### 6.2 每页正式内容结构

前台标准 8 项：

1. 页码；
2. 页面类型；
3. 叙事职责；
4. 本页发生的新事实；
5. 最终文字；
6. 画面证据；
7. 前后页承接；
8. 制作备注（可选）。

约束：

- “画面证据”替代泛化的“画面描述”；
- 叙事职责允许系统 / AI 建议，不锁死为枚举；
- 制作备注只记录特殊生产要求；
- 人物、场景、表情、动作不拆成大量手工字段，优先自动解析。

### 6.3 版本

保留 ContentPage / PageVersion / ContentCopyRevision 的稳定身份 + append-only 正式版本原则。

V2 新内容字段采用稳定结构化 payload，避免无上限增加数据库列。

建议 schema：

- `narrative_role`
- `new_fact`
- `final_copy`
- `visual_evidence`
- `continuity`
- `production_note`

正式 Revision 仍然是整篇确认快照，不覆盖旧正式版本。

---

## 7. 公众号图文文章

图文文章不强行使用 ContentPage 逐页模型。

主体为：

- 标题；
- 摘要；
- 正文；
- 配图建议 / 配图关联。

已确认：**图文文章配图不强制进入正式批量生图体系。**

默认在公众号制作阶段按需处理；只有确实需要统一风格、成组 IP 场景图或正式图片生产时，才调用图片批次能力。

---

## 8. AI 内容导入

AI 是主要录入方式，不让用户重复录入 AI 已经完成的工作。

流程：

```text
工作台生成 AI 创作要求
↓
复制给 AI
↓
AI 输出结构化结果
↓
整段粘贴回工作台
↓
系统解析
↓
变更预览
↓
用户确认
```

支持：

- 首次完整导入；
- 部分页面更新；
- 单字段 / 单页面更新；
- 不覆盖未变内容；
- 导入前显示差异；
- 导入后形成新的 Working Copy / 版本记录。

固定项目规则、栏目收尾句、固定封底等不要求 AI 每次重新生成。

---

## 9. 图片制作批次

图片生产采用“批次优先”，不采用“每张图片人工维护完整 Prompt”。

### 9.1 批次输入

前台主要维护：

- 整批生图说明；
- 整批备注。

系统自动解析：

- 各页内容；
- 人物；
- 场景；
- 特殊要求；
- 缺失人物 / 场景资产。

### 9.2 执行方式

支持：

- 整批生成；
- 先做试样；
- 选择部分页面生成；
- 单页 / 部分页面返修。

试样不强制第一页。

### 9.3 审核

支持：

- 整批通过；
- 整批通过但指定页面退回；
- 单页退回 + 批注。

返修任务由系统根据原批次要求 + 当前页面要求 + 最新审核批注自动重组。

---

## 10. 视频制作

### 10.1 不重复维护内容概览

视频不重复录入：

- 视频名称；
- 核心表达；
- 视频故事线；
- 视频表现重点。

这些继承同一 Content Item，只以“来源 ›”弱显示，需要时查看。

### 10.2 前台主要输入

视频制作页只保留：

1. 整批视频制作说明；
2. 完整旁白稿；
3. 视频片段。

每个片段主要信息：

- 来源图片 / 来源页（系统自动）；
- 动态说明；
- 建议时长（AI / 系统建议，可改）；
- 对应旁白（系统自动分配）；
- 制作备注（可选）。

原则：

> **图片记录“画面是什么”；视频记录“画面怎么动、动多久、怎么说”。**

### 10.3 旁白与时间轴

完整旁白只维护一份正式稿。

系统自动：

- 将旁白分配到一个或多个视频片段；
- 根据计划时长计算预计时间轴；
- 检查旁白超时；
- 检查总时长和明显节奏异常。

前期不要求人工维护绝对秒数。

精确时间轴属于剪辑 / 成片结果。

### 10.4 只选择视频号时

已确认采用方案 A：

> **不额外暴露独立“基础图片批次”流程。**

视频号自己的“制作”内部自动包含：

```text
基础图片准备 / 生成
↓
视频化
```

前台仍保持一个“视频制作”入口。

---

## 11. 统一媒体批次模型

后台新增统一批次概念，前台不显示技术名。

### 11.1 MediaBatch

代表一次图片或视频生产批次。

主要承担：

- 批次类型（image / video）；
- 所属 ContentBranch；
- 批次说明；
- 批次备注；
- 执行范围；
- 状态；
- AI 任务快照；
- 创建 / 审核时间。

### 11.2 MediaUnit

代表批次中的单个执行单元。

图片通常对应页面；视频通常对应来源图 / 片段。

用于：

- 单页 / 单段返修；
- 单位级审核；
- 局部重新生成；
- 记录计划时长、动态说明等差异信息。

用户不需要手工维护复杂 Unit 表格，系统根据正式内容和批次解析自动创建。

---

## 12. 人物与场景资产

### 12.1 资产检查

系统按整批聚合人物 / 场景，不逐页重复警告。

示例：

```text
人物
妈妈 ✓
弟弟 ✓

场景
家庭玄关 ✓
儿童医院候诊区 ⚠ 新场景
```

### 12.2 新场景

首次使用新场景时，Work 按既有本地 SOP 建立长期可复用标准场景 / 参考图。

如果正式生产图本身已经适合作为场景参考，不重复制造母版。

时间、光线、人物、道具属于本次使用变化，不因此新建多个场景实体。

### 12.3 新人物

只为长期可能复用的身份建立人物资产；普通路人不进入人物库。

工作台只关心：

- 是否已有；
- 本次是否新增；
- 后续可否复用。

不在 V2 前台建设复杂 DAM。

---

## 13. 审核与状态

### 13.1 统一审核动作

所有内容 / 图片 / 视频尽量统一为：

- 通过；
- 退回修改 + 批注。

### 13.2 状态自动化

状态尽量由行为推导，不要求用户手工维护大量状态。

### 13.3 渠道流程

默认只显示：

```text
制作 → 审核 → 发布
```

配音、剪辑、字幕、排版等只是“制作”内部子项，不升级成复杂主流程节点。

未来允许简单增删改顺序，但不建设低代码流程编辑器。

---

## 14. 进行中 / 待我审核

### 14.1 进行中

日常总览保持简单矩阵：

```text
内容 | 公众号 | 视频号 | 小红书 | 下一步
```

目标是 5 秒内知道每个内容做到哪里。

### 14.2 待我审核

由系统根据内容 / 图片 / 视频进入审核状态自动聚合，不要求用户手工加入审核列表。

---

## 15. 来源与规则

### 15.1 业务来源链

灵感 → 选题 → Content Item → ContentBranch 是真实业务关联，不用 SourceReference 冒充。

### 15.2 SourceReference

继续专注：

- 本地规则文件；
- SOP；
- 台账；
- 规范；
- 其他外部来源引用。

不把 Inspiration / Topic 来源关系塞进 SourceReference。

### 15.3 Work 本地规则

工作台不重复告诉 ChatGPT Work：“读取哪个 MD / 哪个 SOP”。

本地 Work 自己处理已有规则和参考文件。

工作台只输出当前批次新增的生产意图与差异要求。

---

## 16. AI 任务快照与追溯

每次复制 / 执行：

- 整批任务；
- 试样任务；
- 部分生成任务；
- 返修任务；

系统自动保存当时实际形成的任务文本及关联版本。

日常前台弱化展示，需要追溯时才查看。

---

## 17. 上游修改影响

上游内容修改后，不粗暴清空下游生产结果。

系统提示：

> 来源内容已修改，当前图片 / 视频基于旧内容，建议复核。

用户选择：

- 继续沿用；
- 重新制作受影响部分。

系统不自动重置整条链。

---

## 18. 数据库与迁移策略

由于历史业务数据允许清空，V2 采用**fresh V2 schema**策略，而不是兼容迁移策略。

实施原则：

1. 在 V2 分支建立新的最终 schema；
2. 旧 V1 业务数据不迁移；
3. 不编写旧 ProductionTask / ChannelTask 到 V2 的 backfill；
4. 不保留为兼容旧数据而存在的冗余字段；
5. V2 稳定后整理 / squash 业务 migrations，确保 fresh install 直接得到清晰 V2 schema；
6. 保留通用 auth / framework 需要的基础 migration；
7. 开发期可暂用中间 migration，最终合并前清理成可维护基线。

## 19. 第一阶段前台结构

V2 第一阶段建议主导航：

- 进行中；
- 灵感；
- 选题；
- 内容库；
- 待我审核；
- 项目 / 栏目设置。

人物 / 场景 / 来源规则默认不是高频主导航，按需从内容制作或项目设置进入，避免工作台变重。

## 20. 明确不做

V2 当前不优先建设：

- 甘特图；
- 工时管理；
- 复杂负责人体系；
- 多级审批；
- CRM；
- 复杂 RBAC；
- n8n 式流程；
- Prompt 参数管理（Seed / CFG 等）；
- 每页完整 Prompt 表单；
- 复杂 DAM；
- 自动修改长期规则；
- 全平台自动发布；
- Premiere / 剪映式时间轴编辑器。

## 21. 实施顺序

建议按以下顺序开发，避免再次形成“大总控页”：

1. **V2 数据模型基线**：Inspiration / Topic 精简 / ContentItem / ContentBranch / 新内容版本关系；
2. **基础导航 + 进行中骨架**；
3. **灵感池 + 选题池 + 开始创作**；
4. **图片文章内容结构 + AI 导入 / diff preview**；
5. **图片 MediaBatch / Unit + 审核 / 返修**；
6. **视频制作 + 旁白自动分配 + 时长**；
7. **公众号图文文章**；
8. **人物 / 场景存在性与新增资产回传**；
9. **待我审核 / 总览完善**；
10. **删除已被 V2 替代的 V1 冗余代码、旧路由、旧测试和旧文档**；
11. **fresh migration 基线整理 + 全量回归验收**。

每一阶段都遵守：

> 先自审 → 开发 → 测试 → 再自审 → 汇报。

遇到影响产品方向、操作习惯、数据主关系的决策必须请示用户；局部技术问题、明显 bug、无争议的小优化直接处理。

## 22. 成功标准

V2 达标时，日常使用应该接近：

```text
记灵感
→ 选题
→ 开始创作并选渠道
→ 复制 AI 任务
→ 粘贴 AI 结果并确认差异
→ 生成 / 审核图片
→ 生成 / 审核视频
→ 发布
```

用户不需要理解 ProductionTask、ChannelTask、MediaUnit、Revision ID 等技术概念。

最终判断标准不是“后台对象是否完整”，而是：

> **是否明显减少重复录入、减少状态维护、减少找文件和确认进度的成本，同时又能保留正式版本和生产历史。**
